# Протокол встречи 16.09.2026 (10:05)

Разбор вопросов конкурсантов по кейсу трессировки тепловых сетей.

## ИТОГИ / ДОГОВОРЁННОСТИ

1. Стек жёстко ограничен: Java 11, Spring Boot, Spring Data. Kotlin, другая версия Spring, C++ и прочие отклонения — на риск команды (не задеплоится и не проверится на стендах). ИИ для конвертации кода использовать можно, оценивается результат. Вариант «внешний контур на Kotlin, ядро на другом языке внутри Docker» не принимается — всё решение должно быть на Java 11.

1. Атрибуты решения: UI не нужен (чистый сервис: входные данные → выходной файл GeoJSON), качество визуализации не оценивается, важна корректность GeoJSON. Swagger/сопроводительная документация к API — желательна. PostGIS — допустим. Отдельный контейнер фронтенда — не обязателен и не оценивается.

1. Ресурсы: несколько серверов нельзя — сервис в единственном экземпляре на первом этапе; заложить горизонтальное масштабирование можно, но не жёстко. Ограничений по CPU не заявлено. Ограничений по времени обработки файла нет, но быстродействие — дополнительный критерий оценки. Программа полностью офлайн, без агентов с токенами. Команды передают репозиторий с исходниками и скриптами деплоя (Maven и Gradle), эксперты разворачивают и проверяют на своих мощностях; для демонстрации на защите команда может развернуть у себя.

1. Датасет изменён: вместо подключения ОКС даётся конкретная точка подключения, геометрия ОКС не влияет; объектов — тысячи в масштабе города. Часть сведений урезана (критическая инфраструктура, ИБ). Ориентир по объёму входных данных — реально до 2–3 ГБ, не запас «на будущее».

1. Геометрия: угол пересечения считается от оси препятствия (ось строит команда); для полигональных объектов расстояние меряется от внешней границы полигона, для линейных — между внешними границами расчётных габаритов по таблице 4.3. Для дорог и трамвайных путей — 3 м за границей/буфером. Правила — по СП «Тепловые сети», организаторы готовы консультировать по интерпретации.

1. Глубины: шага 0,5 м в актуальном приложении нет; минимум 0,7 м — это минимальное отклонение по глубине от пересекаемого препятствия; обычная глубина 3 м; удорожание за каждую дополнительную величину заглубления. Близкие пересечения разрешено объединять в один подход без возврата на 3 м (критерий близости уточняется в рабочем порядке).

1. Диаметры и предельные длины: при превышении предельной длины непрерывной части одного диаметра допускается поднять диаметр на одну номенклатуру (200 → 250), не более. При разветвлении без смены диаметра протяжённость суммируется по номенклатуре; при разных диаметрах — считается отдельно. По датасету такие случаи не встретятся. Существующая сеть по геометрии не проверяется.

1. Камеры/узлы: логической разницы между тепловой камерой, техузлом и врезкой нет; камера — узел с несколькими лучами, врезка — новый единственный луч. Новая тепловая камера обязательна в каждой точке разветвления. Если точка врезки ближе 10 м к существующей камере — приходим в камеру, если дальше — строим новую врезку; при нескольких камерах в радиусе 10 м выбирается оптимальная по стоимости. Несколько новых веток к одной камере — это несколько независимых врезок. Реконструируем только часть существующего отрезка; реконструкцию камер, не являющихся точками врезки, обсчитывать не нужно.

1. Оценка: критерий минимизации — протяжённость и стоимость с весами 0,7 и 0,3; нестандартные углы отвода (не 45°/90°) — полуторакратное удорожание и обязательная минимизация поворотов. При наложении зон нескольких препятствий берётся максимальный коэффициент, один спецучасток на весь участок, без перемножения. Округление расстояний допускается в большую сторону при незначительном отклонении (4,999 → 5 м). Невалидная геометрия на входе — возвращаем диагностическую ошибку. Неподключение ОКС допускается при дороговизне трассы — работает система штрафов.

1. Два этапа оценки: на первом сравниваются горизонтальные проекции трессировок с эталонной геометрией, Z-координата и расчёты углублений — только на втором этапе (до 10 наиболее интересных решений). Дополнительные обоснованные критерии стоимости, вариативность препятствий (метро, детские сады, школы, водные преграды, трамвайные линии) и универсальность алгоритма под другие ресурсы (водоснабжение, кабели) — плюс к оценке.
